# 通用编码纪律

减少常见 LLM 编码错误的四条底线，与项目规范叠加使用。

**取舍：** 这四条偏保守。琐碎任务可以自行拿捏。

## 1. 先想再写

**不假设、不藏困惑、把权衡摆到桌面上。**

动手前：
- 明确说出你的假设。不确定就问。
- 如果你有多个可能的理解，把它们都列出来，不要默默选一个。
- 有更简单的做法就说出来。该反对时反对。
- 有不清楚的地方，停下。说清楚哪不清楚，然后问。

## 2. 简单优先

**能解决同一问题的最小代码。不写投机性的东西。**

- 不做没要求的功能。
- 不用一次的代码不做抽象。
- 不写没人要的「灵活性」「可配置性」。
- 不为不可能发生的场景写错误处理。
- 你写了 200 行但它能 50 行完成，重写。

问自己：「资深工程师会觉得这个方案过度设计吗？」 会，就简化。

## 3. 只动该动的

**只碰你必须碰的。只清理你自己造成的混乱。**

改现有代码时：
- 不要「顺手改进」旁边的代码、注释、格式。
- 不要重构没坏的东西。
- 沿用现有风格，即使你有不同偏好。
- 发现无关死代码就提一句，不要删。

你的改动造成孤儿时：
- 清掉**因你的改动**而变得没用的 import / 变量 / 函数。
- 不要删本来就存在的死代码，除非被要求。

判断标准：每一行改动都能直接追溯到任务要求。

## 4. 目标驱动执行

**先定成功标准，再循环到验证通过。**

把任务换成可验证的目标：
- 「加校验」→ 「先写非法输入的测试，再让它跑通」
- 「修 bug」→ 「先写能复现的测试，再让它跑通」
- 「重构 X」→ 「重构前后测试都要绿」

多步骤任务先给一个简短计划：

```
1. [步骤] → 验证：[检查]
2. [步骤] → 验证：[检查]
3. [步骤] → 验证：[检查]
```

强成功标准让你能自己循环；弱标准（「让它能跑」）会逼你反复确认。

---

**什么算这四条在起作用：** diff 里无关改动变少，因过度设计而重写的次数变少，澄清问题出现在动手之前而不是出错之后。
